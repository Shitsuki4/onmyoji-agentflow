# 使用日常与周常计划

适用于 `feat/upstream-workflow-pipeline` 开发分支。本机发布安装仍是 `v0.1.9`，本轮没有替换或重启专用 MCP，也没有运行游戏任务。转换候选需要用户本人审批；没有真实回放的候选仍是 `verification: unverified`。

## 先看有哪些任务可以执行

```powershell
oaf marathon --plan daily --preview
oaf marathon --plan weekly --preview
oaf marathon --plan all --print-plan
```

预览只读，不获取模拟器控制器，不创建运行目录。它会检查源码版本、待审更新、参数、账号档案、开放日程、依赖、持久检查点及冷却。`blocked` 表示尚缺前置条件，不会为这项任务先导航或消耗资源。

`daily` 包含签到、补给、友情点、蓝票单抽、食盒、寄养、日活战斗、花合战、地域鬼王及寮任务入口；`weekly` 包含蓝票、黑蛋、秘闻和斗技入口。**列入计划不代表相应整段上游脚本已经转换。** 地鬼、秘闻、斗技和大部分寮活动目前仍显示待转换/待账号核对。

## 本轮实际生成的转换

下表是独立任务范围，不是整个所属脚本的转换完成声明。原始整段 `DailyTrifles`、`RichMan` 等仍保留在转换队列中。

| 上游标识 | 独立范围 | 资源与边界 |
|---|---|---|
| `oas:DailyTrifles#store_sign` | 商店免费签到 | 不执行召唤、购买体力或吉闻；需要奖励画面作为回执 |
| `oas:DailyTrifles#friend_love` | 友情点收取 | 不发送祝福、消息或邀请；没有回执不能记完成 |
| `oas:DailyTrifles#one_summon` | 每日蓝票单抽 | 最多一张蓝票、一次画符；不执行今忆、神秘图案或补票 |
| `oas:TalismanPass#task_rewards` | 花合战任务奖励 | 不处理等级自选、1500签御魂或付费奖励 |
| `assttyys:func:700#food_boxes` | 体力/经验食盒 | 不更换育成式神；经验已满时停止 |
| `oas:RichMan#medal_blue` | 勋章商店一张蓝票 | 源码价格 180 勋章；核对剩余数量、余额和确认画面价格 |
| `oas:RichMan#medal_black` | 勋章商店一颗黑蛋 | 源码价格 480 勋章；同样只允许单件窗口 |
| `assttyys:func:022` | 普通召唤画面组件 | 不是从庭院开始的完整每日抽卡任务；需普通召唤画面及破碎咒符确认 |

这些配方只匹配 `data/translations/pins.yaml` 中已审计的完整源码/依赖/资源指纹。上游发生变化会回到 agent 转换队列，不能自动更新白名单继续套旧逻辑。源码只作静态数据读取，不运行 Python/AutoJS 上游程序。

OAS `summon_one` 有外层循环，没有“一抽后立即结束”的硬计数条件。本项目为 `#one_summon` 单独定义一次性契约：票数 OCR 不可靠则停止，选择蓝票前预扣一张预算，画符前再次确认，看到抽卡结果才记录业务完成。若中途异常，预算保留为保守估计，不因没有回执自动退还并重抽。

单抽和两项周常购买默认 `enabled: false`，相应 `mystery_amulet` / `medal` 预算默认 0。需要真实账号档案、用户批准与相应预算才能执行。不得把“单抽”说成免费蓝票，也不得为通过预览而伪造 `verified` 或账号证据。

## 开始与恢复

先完成审核、观察和小规模验证，再运行计划。例如仅处理一轮可用项：

```powershell
oaf marathon --plan daily --rounds 1
```

经过验证后，持续检查一天的开放窗口和冷却：

```powershell
oaf marathon --plan all --hours 24
```

不传时长和轮数时，仍采用一轮即停。传 `--hours` 且不传 `--rounds` 时，不会因默认一轮而提前结束。进程需要持续运行；没有创建 Windows 定时任务。长驻的上游定时同步仍由 `upstream.schedule` 配置控制。

命名计划默认 `sync_before_start: true`：每次启动先自动拉取、建立增量目录并处理转换队列；同步阶段不占用设备租约。拉取失败、同步报告含错误或识别/源码更新仍待审批时，整轮停止。不会因为最新报告写着 `unchanged` 就忽略更早的待审资源更新。

CLI 用历史记录的 `job_id` 传给 `--resume`；MCP 用 `marathon_start` 的 `resume_job_id`。恢复沿用原账号、实例与计划，但创建新的运行记录。已核验完成的项跳过；`running` 或 `needs_review` 的不确定步骤不会被自动清除或重放。修复获批不等于已证明上一次花费没有发生。

## 编排自己的任务

```yaml
durable: true
task_aware: false
sync_before_start: true
home_between: true
items:
  - id: collect
    program: oas:DailyTrifles#friend_love
    task_key: friend_points
    scope: daily
    once_per_period: true
  - id: flower
    program: oas:TalismanPass#task_rewards
    task_key: flower_task_rewards
    after: [collect]
    once_per_period: true
```

`after` 引用本计划内唯一的 `id`，按依赖顺序执行；循环、未知依赖或重复 ID 在启动前报错。依赖必须有当前周期的真实完成证据，执行进程正常退出不能代替业务完成。

| 字段 | 意义 |
|---|---|
| `scope` | `daily` 或 `weekly`；按账号时区及重置小时切周期 |
| `task_key` | 同账号跨计划共享的任务身份，优先于 `id`；不要为绕过检查点改名 |
| `once_per_period` | 本周期有完成/已完成回执后不再执行 |
| `limit_per_period` | 本周期自动执行成功次数上限 |
| `min_interval_min` | 两次已确认完成之间的持久最小间隔 |
| `after` | 依赖任务 ID 列表 |
| `schedule` | 开放日期、星期和时间窗口 |
| `schedule_profile` | 使用 `game.schedules` 中有证据的账号日程 |
| `profile` | 使用 `game.profiles` 中核对过的队伍、难度及参数 |
| `on_failure` | 默认 `pause`；`continue` 只允许处理其他独立项，不会清除当前不确定状态 |

`schedule.weekdays` 使用 1–7（星期一到星期日）；`windows` 为 `[["HH:MM", "HH:MM"]]`，结束时刻不包含在窗口内。跨午夜窗口归属开始日；开始和结束相同表示整日。`starts_on` / `ends_on` 为 ISO 日期。窗口用于检查任务能否开始；任务内部仍遵守工作流时长与活动边界。

寮宴会、狩猎、寮突破和斗技的真实开放时间不能从示例猜测，故命名计划引用账号日程并在缺少证据时阻塞。秘闻与斗技也需要队伍/难度档案；这些账号字段本轮没有自动填充。

## 四次寄养与故障处理

寄养计划使用每日上限 4、最小间隔 360 分钟，并检查实际寄养到期时间。预先存在的倒计时只同步状态，不计作新增寄养；计数在 SQLite 中持久保存，换计划文件或重启不能立即连寄四次。计数依据本项目的新增成功回执，不推断项目接管前的手动操作次数。

这还不是四次寄养的实机闭环：到期收取/续寄、白达摩身份识别和完整真实回放仍未完成。没有明确可用卡或单位身份时保持安全暂停，不会点击已占用的卡。

开发包也修正了 `active_foster` 抢先把新寄养判为“已有寄养”的条件。真实运行工作区保留着用户未提交的 `foster.yaml`，本轮没有覆盖它；更新已有工作区时仍需单独审阅这一条件变更，不能只升级 Python 代码就声称寄养计数已实机生效。

超时、卡死、循环、识别失败或异常会沿用持久接管包：截图、日志、变量、源码版本和异常信息。模型未启用时保留待接管任务；不会凭空启动一个外部 Codex 进程。诊断修复仍需审批，不自动重跑整轮。

资源动作支持 `recheck: true` 和 `attempt_var`：用户确认后重新取帧核对，再在发送输入前写入一次性尝试标记。这样即使模拟器已收到点击/画符而 IPC 返回报错，局部重试也不会重复购买或抽卡。未知结果保留检查点，不能靠清空变量重试。永久阻塞的原生模拟器调用仍不能靠引擎计时器强制打断。
