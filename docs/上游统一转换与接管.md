## 工作链路

1. 同步 OAS / assttyys 的上游提交，转换识别资源，并把完整源码作为不可执行的文本快照保存。
2. 收录全部任务入口和功能组件，计算源码、传递依赖、配置与识别资源的指纹。
3. 指纹未变化的已处理任务复用结果；新增或变化的任务进入持久转换队列。
4. 简单程序整包转换；大型程序由 agent 分页读取入口、配置、被调用方法和识别资源，再输出统一 `format: 1` 状态机。
5. 格式、安全确认和已有截图回放通过后，生成候选分支，等待用户审批。缺少回放样本明确标为 `unverified`。
6. 已批准的统一工作流可按日常/周常计划编排。上游源码指纹变化后，旧转换停止执行，等待处理新版候选。
7. 超时、画面卡住、循环、无进展、识别失败或程序异常会保存故障包。计划停在当前项，agent 有限诊断并提交修复，继续走原有验证与审批流程。

上游代码不会被 `import`、`eval` 或直接作为 Python / AutoJS 启动。任务目录、资源转换、语义转换、可运行验证是不同阶段，分别报告状态。

## 查看与转换上游脚本

安装包含本功能的代码后，使用已有数据目录：

```powershell
oaf sync
oaf programs list
oaf programs list --source oas
oaf programs compile --limit 2
```

`--limit 2` 只限制这一批；不传时使用 `upstream.translate.max_per_sync`，默认 `null`，保持不限。`compile` 只生成待审候选，不运行模拟器。

需要使用已有缓存而不拉取网络时：

```powershell
oaf sync --offline --no-translate
```

| 队列状态 | 意义 | 后续操作 |
|---|---|---|
| `pending` | 已收录、尚未转换 | `programs compile` |
| `component` | 上游内部功能组件 | 通常随所属任务转换；也可按编号单独选择 |
| `waiting_agent` | 未启用模型，完整源码仍在 | 配置供应商后继续，或由外部 agent 读取并提交提案 |
| `compiling` | 正在转换 | 等待；进程退出后可重新处理队列 |
| `budget` | 达到用户配置的模型预算 | 额度恢复后继续，不丢弃已完成任务 |
| `blocked` | 逻辑不完整、读取未完成、超出上下文/步数，或安全检查失败 | 查看原因和读取记录；修复后显式 `--retry` |
| `failed` | 模型或转换过程报错 | 查看原因后显式 `--retry` |
| `waiting_user` | 有待审候选 | 用户在现有面板审核，agent 不代批 |
| `merged` | 用户已合并候选 | 先观察；该版本首次输入仍需用户确认 |
| `superseded` | 上游已出现新的指纹 | 使用新任务，旧提案不能重新提交 |

`programs source` 使用队列编号读取清单；指定清单里的 `--path` 后，用 `--offset` 和 `--chars` 分页读取。结果包含 `complete` 和 `next_offset`，不会把截断源码冒充完整文件。

外部 agent 可通过 `programs propose` 提交 JSON 文件，内容为 `complete`、`unsupported`、`notes` 和 `workflow`。同一个源码版本不会重复生成候选；不完整的输出、无执行逻辑的占位工作流、外部资源路径、无画面识别的输入和缺少敏感确认的操作会被拒绝。

修订自己尚未批准的草稿可显式传 `--replace-pending`：新草稿验证通过后，旧草稿标记 `superseded`，新草稿重新等待用户审批；相同内容不重复提交，失败修订保留原审批项。不能用它替换已合并版本或绕过审批。

## 自动检查与增量更新

```powershell
oaf config set upstream.translate.all_scripts true
oaf config set upstream.schedule.enabled true
oaf config set upstream.schedule.interval_hours 24
oaf sync --loop
```

也可保持网页面板或 MCP 服务运行；stdio 和 HTTP MCP 都支持配置中的定时同步。启动计划时也会检查已到期的同步。宿主退出后，不再触发新的定时检查；这没有创建 Windows 系统任务，也没有更改其他服务。

同一数据目录的同步、转换均有跨进程互斥。即使上游没有新提交，也会继续处理上次因批量上限或模型预算留下的转换任务。显式配置旧版 `translate.schemes` 白名单时，仍沿用旧版指定方案翻译；清空白名单后才使用全目录转换。

大型程序采用有界读取会话：默认 `max_prompt_chars: 180000`、`max_agent_steps: 24`。读取记录保存到数据目录 `program-transcripts/`，同一源码指纹可以继续读取。达到上限不会截断逻辑、生成占位代码或自动宣布转换完成；可由外部 agent 接着处理。

## 用统一任务标识编排

计划支持工作流名，也支持上游任务目录中的 `program` 标识。例如将下列内容保存为 `upstream-plan.yaml`：

```yaml
task_aware: false
continuous: false
home_between: true
items:
  - program: oas:AreaBoss
    scope: daily
    task_key: upstream_area_boss
    once_per_period: true
    cooldown_min: 30
    params: {}
  - program: oas:Secret
    scope: weekly
    task_key: upstream_secret
    once_per_period: true
    cooldown_min: 60
    params: {}
```

```powershell
oaf marathon --plan upstream-plan.yaml --preview
oaf marathon --plan upstream-plan.yaml --rounds 1
```

这些标识来自真实 OAS 目录。尚未完整转换并获批的项会显示阻塞并跳过，不会直接启动原脚本。`params` 的具体字段以实际获批工作流为准；空字典采用其默认参数，不能据此推断账号队伍、难度或购买预算已核对。

每日四次寄养、到期收取/续寄、周商店、秘闻竞速与斗技仍需要各自的真实画面、账号配置和完成证据。编排层接入任务标识不等于这些玩法已经形成实机闭环。

## 故障后让 agent 接管

```powershell
oaf handoffs list
```

`handoffs show` 按编号读取故障包，包含运行编号、最后截图、工作流全文、源码版本、变量、近期状态、日志和异常回溯。`handoffs diagnose` 调用已配置模型；外部 agent 可用 `handoffs propose` 提交修复 ops。两者均只做有界诊断/修复，不会自动恢复整轮计划。

日常计划默认启用诊断；`--no-repair` 会只留证据，不调用模型。即使不调用模型，故障包也会跨会话保留。预算不足、账号前置条件、设备连接问题及用户拒绝会保留给用户处理，不能通过修补工作流绕过。

修复后继续运行前，应检查审批结果并重新观察。工作流已经变化时，旧故障包会拒绝继续修补，避免把旧截图套到新版逻辑。购买、抽卡等操作仍逐项确认。

这里覆盖的是引擎能够检测到的工作流超时、卡住和异常。若原生模拟器调用本身永久阻塞，引擎内的计时器不能强制中断它；当前代码不会据此强杀模拟器或让第二个 agent 绕过设备锁同时点击。
