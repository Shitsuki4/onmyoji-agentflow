# onmyoji-agentflow 项目评估与改进建议

评估日期：2026-11-20。运行代码基于 v0.1.8 / `f3d13d61d849d22dc96a9412751161af1623e1ce`；本轮 `git ls-remote origin refs/heads/main` 确认远端 main 仍为该提交。本地另外有寄养实测和用户选卡规则的文档提交。

项目已有工作流引擎、识别、失败监管、上游同步、CLI、网页和 MCP 的基础。当前最影响本号使用的是：调度还不能依据游戏任务进度决定做什么、做多少和何时结束；跨入口运行管理、资源预算和完成证据也尚未形成统一机制。建议先把这些做好，再扩充玩法。

本报告分清三种证据：离线复现的具体缺陷、代码可确认的设计缺口、值得新增的功能。离线复现只使用 `ReplayDevice`，本轮评估没有向游戏输入点击或滑动，也没有修改运行代码。不能据此声称账号已发生误购买、双端抢点或重复刷本。

## 1. 优先修复的具体问题

P1 表示应在下一轮无人值守运行前优先处理；P2 表示随后完善。

|---|---|---|---|---|

### E-01：三项缺陷的复现

- `source_type`：command，内存中的离线回放；`content_hash`：n/a。
- `source_ref`：本轮在仓库根目录执行下面命令；代码位置相对于 `src/onmyoji_agentflow/`。
- 原始输出：动作上限一、实际三；剩余次数一；删除单个购买保护仍通过。

在已安装项目测试依赖的 Windows PowerShell 中，从仓库根目录执行：

### P-01：动作限额的调用路径

`Runner.run()` 检查本 tick 的动作总数 → 匹配一个状态 → 遍历该状态全部 `do` → `_do()` 逐次点击并累加 → 下一 tick 才重新检查限额。E-01 对应 F-01；应把检查下移至每个动作执行前，并保留外层检查。

### P-02：已达标后重试的调用路径

`Supervisor.run()` 得到失败结果 → 根据本次结果调用 `remaining_params()` → `max(1, target - completed)` → 新建一次 Runner。E-01 对应 F-02；应区分尚需开战和只需退出结算，不能用一作为所有重试的最小额度。

## 2. 已确认的设计缺口

E-02 为上述版本源代码及本轮静态阅读；相关文件均可在该提交核对。E-03 为本机日志与[经验库](经验库.md)第 9 节的实机记录。这里的并发及断点问题没有通过同时启动真实游戏任务来验证，以免干扰账号。

| 编号 | 优先级 | 当前不足及证据 | 值得做的改进 |
|---|---|---|---|
| F-05 | P1 | 默认计划仅补给、突破、固定十五把拾层和领奖；`next_ok` 只在内存保存，采用启动后若干分钟冷却，不读取游戏日/周进度，也没有完成全部目标后退出条件。见 `marathon.py:26`、`:92`、`:182`、`:197`，E-02。 | 建立按账号、游戏重置日和周次持久化的任务账本，保存任务完成数、领奖状态和证据；重启后先核对现状。单次执行完可做目标即停，需要到期续寄时单独记录下一次到期时间。游戏重置时刻做配置并实机核对，不能简单按启动后 24 小时算。 |
| F-06 | P1 | 网页用 `Panel.running`，MCP 用 `McpServer.jobs`；锁是各进程内的线程锁，CLI、marathon 直接调用 Supervisor。见 `web.py:66`、`:119`，`mcp_server.py:226`、`:351`，`cli.py:119`、`:386`，E-02。 | 统一运行入口及持久化设备租约，带 PID、心跳、过期恢复和统一停止。锁按实际模拟器实例归一，不能只按自定义实例名；`127.0.0.1:16384` 和 `emulator-5554` 不得被当作两台设备。设备互斥须跨不同 oaf home 生效。同步/修复也应有跨进程的工作区锁或隔离 worktree。 |

| F-08 | P1 | `home` 对未识别画面有「最多按八次返回」兜底；marathon 的 STOP 文件和 deadline 仅在外层轮询，子工作流运行时不会轮询这个文件或截止时间。见 `data/workflows/home.yaml:271`、`marathon.py:107`、`:146`、`:218`，E-02。 | 把已确认安全的弹窗处理做成共用识别；未知弹窗先留图、暂停输入。让停止、deadline 和预算检查能传至子工作流，提供「当前战斗结束后停」与「立即停止输入」两种明确选项。现有 STOP 等待当前项目结束符合 README，但不等于紧急停止。 |

## 3. 最值得新增的功能

| 顺序 | 功能 | 本号的直接收益 | 首次实测的完成标准 |
|---|---|---|---|
| 1 | 任务扫描与按缺口执行 | 花合战 12/15 时只补三次；已经领满活跃也能继续明确列出未完成日常，不混淆两个目标。 | 读取今日和本周列表并关联任务名、当前值、目标值、领奖状态；运行前后截图核对，目标完成后无多余开战。 |
| 2 | 寄养选卡、收取和到期续寄 | 补上当前遗漏，并按用户收益偏好选卡。 | 同区和跨区检查候选；先星级降序，再按太鼓 > 斗鱼 > 伞室内 > 其他变异结界卡 > 太阴排序。同星级同类型再比较剩余时长；确认寄养倒计时，持久化到期时间，已有寄养不重复放入。 |
| 3 | 结界收菜与育成维护 | 收结界卡经验、取出满级育成式神并放入明确允许的未满级式神，增加日常收益。 | 每个式神逐个核对；不把「换育成位」误实现成消耗式神。太鼓/斗鱼/其他资源收取分别记账，结果不靠点击次数推断。 |
| 4 | 周活工作流与去重 | 当前只查看过周活，默认计划没有实际推进周任务的工作流。 | 先做已解锁且练度适合的不同地域鬼王和式神委派等目标；按地域或任务实例去重，完成后读游戏计数。难度依据练度和收益选，不直接使用默认一级。 |
| 5 | 活动日历与兑换助手 | 区分打 Boss、刷票和商店兑换，避免过期活动空跑或门票浪费。 | 截止日期和门票可用性核对，兑换先列数量、货币、每日/总限额及费用；只在预算和授权内执行并复核余额。 |
| 6 | 弹窗采样和规则调试台 | 把「截图留在目录」变成可维护的识别数据，减少同样的卡点反复出现。 | 自动按相似画面去重，能标注正确页面、OCR 区域和允许动作；修改后运行正反例回放、观察模式和有限试跑，再发布。 |
| 7 | 账号练度与阵容档案 | 避免只凭攻略名称换阵容，减少突破失败和低效御魂。 | 保存实际御魂套装、面板速度、暴击等实读数值及测量时间；换一件核对一次，最后确认出手顺序。先提供只读建议和三把对比，不直接自动大规模换御魂。 |
| 8 | 每日完成报告 | 能说明做了什么、为何跳过、资源花在哪和哪些需要人工处理。 | 分开记录游戏任务完成、奖励已领、流程已运行和未来待办；寄养写到期时间，未知界面链接到样本。报告支持复制或本地查看，不默认向好友或其他人发送。 |
| 9 | 环境与计划自检 | 提前发现 OCR 缺失、同设备配置重复、资源版本不一致、无回放样本和过期活动。 | 增加只读 `oaf doctor`，检查设备身份、截图尺寸、玩法前置条件、工作流依赖、计划参数和样本数量；给出明确缺项及处理方法，不自动更改系统设置。 |

本号已稳定完成拾层实测，短期先沿用可验证的阵容；「平均一把约 74 秒」来自 11-17 的经验，不是当前所有试跑的统一测速。11-20 的三把组总计 288.8 秒、十二把组总计 1097.9 秒，含进入及结算，不能当作纯战斗时长。需要优化时先把加载、识别、备战、战斗和结算分别计时。

## 4. 建议实施顺序

1. **先修执行边界**：F-01 / F-02 / F-03 / F-04，统一设备互斥、动作级取消和资源记账。验收是在离线回放中不超步数、不额外开战、不丢单项保护、不把页面失败报成完成；随后仅在实机做有限试跑。
2. **再补日活闭环**：任务扫描、持久化完成记录、寄养和结界收菜、完成后领奖并停。寄养排序直接使用用户明确规则，不把「未放卡也能寄养」当作优选策略。
3. **随后推进周活和活动**：按任务缺口运行实际周活，加入活动有效期和兑换状态，再完善面板、规则标注和账号档案。

每个变更独立开分支、补真正覆盖风险的测试、先观察再小规模实测，随后全套回归、推送 PR、CI 通过后合并发版。评估文档本身不表示这些改进已落地。

## 5. 验证边界

三项 E-01 离线复现已完成。F-04～F-12 主要为静态检查确认的行为与功能缺口；涉及真实并发、游戏崩溃恢复、活动新版本及用户账号的边界场景，实施后仍需专门实测。本轮没有通过真实购买、消耗式神或故意使模拟器崩溃验证这些问题。

测试环境还暴露了一个维护问题：项目运行虚拟环境安装了真实 OCR，部分合成图回归没有注入替代识别器，整套测试因此明显变慢。本轮中止了该环境下尚未完成的全套回归，另用与 CI 一致的 `[test]` 环境检查现有测试；不能将后者的结果当作已完成真实 OCR 全套验证。建议单元测试明确注入识别器，真实 OCR 样本另建集成测试任务，以便同时保证速度和真实性。
